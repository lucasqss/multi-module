Guia do projeto Processo

O que o sistema faz, como as peças se encaixam e por onde começar. Leitura de uns 10 minutos.

Java 25 Quarkus 3.33 Oracle Maven multi-module

Em um minuto

O sistema cuida de processos: pedidos que nascem abertos e terminam concluídos, recusados ou cancelados. Há dois tipos de processo, imobiliário e veicular, e os dois andam pelo mesmo motor. O que muda de um tipo para outro fica num pedaço separado, o segmento.

Um motor para todos

Criar, processar e cancelar funcionam igual para qualquer tipo. O veicular entrou sem mudar o motor.

Tipos como peças

Cada tipo traz só o que é dele: seus dados, suas regras e a decisão de aprovar ou recusar.

Escrever e ler separados

Um módulo grava (processo-core), outro só consulta (processo-query).

Bordas trocáveis

Pedidos chegam por API ou fila; sistemas de fora (cadastro, PDF) ficam atrás de interfaces.

CRUD sem cerimônia

O que é só cadastro (agências) segue um caminho bem mais curto, sem motor.

Regras viram teste

Quem pode usar quem está escrito em testes: quebrou a regra, quebrou o build.

Os módulos

O projeto é dividido em módulos Maven (partes que compilam separadas) e gera um único programa. A seta mostra quem usa quem.

Por que um programa só, e não vários serviços? Com até 1.000 usuários por dia em horário comercial, um programa dá conta com folga, e o pagamento e a situação do processo mudam juntos numa única transação. A justificativa completa, com os prós e contras, está na ADR 0013.

MóduloO que temO que não pode
jpa-coreAs tabelas do banco (entidades e scripts de criação).Ter regra de negócio.
processo-coreTodas as regras: o motor, os segmentos e os cadastros.Saber que existe HTTP ou fila.
processo-queryAs consultas (só leitura).Usar as regras do core.
integracoesA conversa com sistemas de fora: cadastro e PDF.Ser chamado direto; só por interface.
processo-appPor onde os pedidos chegam (API e fila) e a montagem do programa.Ter regra de negócio.

Dentro do motor e de cada segmento, as pastas seguem sempre o mesmo padrão:

domain/        as regras, em Java puro (sem framework)
application/   o motor, os segmentos e as interfaces do que vem de fora
adapter/       a parte técnica: banco, transação

A vida de um processo

            processar                     aprovado
ABERTO ──────────────────► EM_PROCESSAMENTO ─────────► CONCLUIDO
   │                                │
   │ cancelar                       │ recusado
   ▼                                ▼
CANCELADO                       RECUSADO (com o motivo)

Criar

  1. O pedido chega pela API (POST /processos/imobiliarios) ou pela fila.
  2. As regras conferem: primeiro as que valem para todos (nome, CPF, valor), depois as do tipo (ex.: a avaliação do imóvel) e, por último, o sistema de cadastro, para não chamá-lo à toa.
  3. O processo é gravado com um número (IMO-2026-000042) e fica ABERTO.
  4. O PDF de abertura é pedido. Se o sistema de PDF falhar, o processo continua criado.

Processar e cancelar

  1. O processo vai para EM_PROCESSAMENTO. Se duas pessoas pedirem ao mesmo tempo, só uma consegue; a outra recebe um aviso de conflito.
  2. O segmento decide: o imobiliário recusa acima de R$ 1.000.000; o veicular recusa veículo com mais de 10 anos.
  3. O processo termina CONCLUIDO ou RECUSADO, com o motivo.

Cancelar só vale enquanto o processo está ABERTO.

As respostas da API

CódigoQuando
201 / 200 / 204Deu certo (criado / processado / cancelado).
422Uma regra recusou o pedido. O motivo vem no campo detail.
404O processo não existe.
409Outra pessoa mudou o processo ao mesmo tempo. Tente de novo.
503O sistema de cadastro está fora do ar.

Todo erro vem no mesmo formato (Problem Details):

{"type": "/problemas/regra-violada", "title": "Regra de negócio violada", "status": 422,
 "detail": "CPF inválido: 12345678900"}
Pela fila, a mesma criaçãoUma mensagem na fila processos.imobiliarios.novos cria o processo como a API. Se a mesma mensagem chegar duas vezes (o que é normal em fila), o processo não é criado de novo: o id da mensagem serve de chave. A resposta, criado ou recusado, volta em outra fila.

Motor, segmentos e estados

O motor faz tudo o que é igual para todos os tipos. O segmento só preenche o que é dele:

O motor faz (igual para todos)O segmento faz (cada um o seu)
A ordem dos passos de criar, processar e cancelarOs dados próprios (imóvel, veículo)
As regras comuns e a consulta ao cadastroAs regras próprias
O número do processo e a gravaçãoA decisão de aprovar ou recusar
Os estados e as mudanças permitidasA tabela própria no banco

Um segmento novo estende SegmentoBase e escreve só duas coisas, as regras e a decisão:

// resumido
@Singleton
public class SegmentoVeicular extends SegmentoBase<DadosVeiculares> {
    public Especificacao<Solicitacao<DadosVeiculares>> regras() { return RegrasVeiculares.TODAS; }
    public Avaliacao avaliar(Processo<DadosVeiculares> processo) { /* aprova ou recusa */ }
}

Os estados ficam num enum. Cada estado diz para onde pode ir; qualquer outra mudança é recusada com 422:

// resumido: no código, cada transição é um método que devolve o próximo estado
public enum Situacao {
    ABERTO           { iniciarProcessamento() → EM_PROCESSAMENTO; cancelar() → CANCELADO },
    EM_PROCESSAMENTO { concluir() → CONCLUIDO; recusar() → RECUSADO },
    CONCLUIDO, RECUSADO, CANCELADO;   // finais: não vão para lugar nenhum
}
Quando um tipo não cabe no motorSe um tipo precisar de estados ou passos que os outros não têm, ele ganha um fluxo próprio. Encher o motor de exceções para um tipo só é o sinal de alerta.

Sistemas externos

O core nunca chama um sistema de fora direto. Ele declara uma interface do que precisa, e o módulo integracoes implementa. Assim dá para trocar o sistema, ou simular nos testes, sem mexer na regra.

SistemaPara quêSe cair
CadastroConfere a situação do CPF antes de criar.A criação para e responde 503.
PDFGera o documento de abertura depois de criar.O processo continua criado; a falha vai para o log.

No modo de desenvolvimento (quarkus:dev) os dois são simulados: dá para rodar tudo sem os sistemas de verdade. Nos testes, servidores falsos fazem o papel deles.

Quando é só cadastro

Nem tudo precisa de motor. Um cadastro de agências só inclui, altera, exclui e consulta: não tem estados, nem tipos, nem fluxo. Por isso segue o caminho curto:

  • um record que já nasce validado (Agencia);
  • um serviço que grava e lê (Agencias);
  • a API em /agencias (AgenciasResource).

A regra prática: é só CRUD, caminho curto. Se aparecer fluxo, estados ou variação por tipo, aí sim vale o modelo do processo.

Como sabemos que está certo

  • As regras de arquitetura são testes. "O motor não conhece os segmentos" e "a API não usa o banco direto" estão escritos no ArquiteturaTest e no ArquiteturaModulosTest. Quem quebrar uma regra quebra o build.
  • O motor é testado sem banco. Nos testes de unidade, versões em memória (fakes) fazem o papel do banco. Um teste de contrato roda as mesmas verificações no fake e no Oracle, para garantir que o fake não mente.
  • O sistema é testado de ponta a ponta. Os testes de integração sobem o programa pronto com um Oracle de verdade e repetem o mesmo cenário para cada tipo, inclusive 8 pedidos simultâneos.
mvn -pl processo-core,integracoes -am test   # rápidos, sem Docker
mvn verify                                    # tudo (precisa de Docker)

Glossário

TermoO que é
ProcessoUm pedido que nasce ABERTO e termina concluído, recusado ou cancelado.
SegmentoUm tipo de processo (imobiliário, veicular), com seus dados, regras e decisão.
MotorA parte que faz o que é igual para todos os tipos (MotorDeProcessamento).
SolicitaçãoO pedido de criação, antes de passar pelas regras.
AvaliaçãoA decisão do segmento ao processar: aprovado ou recusado com motivo.
Cadastro simplesAlgo que é só CRUD (agências). Vai pelo caminho curto, sem motor.
PortInterface do que o core precisa de fora: banco, transação, sistema externo.
AdapterQuem implementa um port com tecnologia de verdade (banco, HTTP) ou recebe pedidos (API, fila).
Value objectUm dado que só existe se for válido, como Cpf e Valor.
EspecificaçãoUma regra que, se não for cumprida, diz o motivo.
Compare-and-setMudar o estado só se ele ainda for o esperado. É o que impede dois processamentos ao mesmo tempo.
Chave de idempotênciaO identificador que impede que o mesmo pedido, repetido, crie dois processos.
Problem DetailsO formato padrão das respostas de erro (type, title, status, detail).
FakeUma versão em memória de algo externo (como o banco), para testar sem ele.
Dev ServicesContainers (Oracle, fila) que o Quarkus sobe sozinho no desenvolvimento e nos testes.

Pontos em aberto

Decidir antes de levar o padrão para produção:

PontoRiscoSaída sugerida
Processo preso em EM_PROCESSAMENTOQueda entre as duas transações do processar.Rotina que reprocessa ou devolve para ABERTO após N minutos.
Corrida na regra da matrículaDuas criações simultâneas passam juntas.Lock, tabela de controle com chave única ou situação copiada para a filha.
Sem histórico de transiçõesNão se sabe quem mudou o quê e quando.Tabela de transições gravada junto do compare-and-set.
PDF sem retentativaChamada síncrona depois do commit (timeout de 2 s); falha só vai para o log.Outbox: tabela de pendências gravada na transação e reenviada por um job.
REST e query com 0% no SonarSó os ITs os exercitam.@QuarkusTest nessas camadas, se o gate exigir.
Lacunas de numeraçãoFalha na gravação deixa número sem uso.Aceitar, ou trocar a sequence por um contador travado na transação, se precisar ser contínua.
