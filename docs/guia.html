Guia do projeto Processo

Como o exemplo de processos de vários tipos com um motor único está organizado em Maven multi-module, por que cada peça está onde está e como estender.

Java 25 Quarkus 3.33 Oracle + Flyway Jakarta Data Padrão State ArchUnit JaCoCo + Sonar

Visão geral

O exemplo tem dois tipos de processo, imobiliário e veicular. Os dois são criados, processados, cancelados e consultados pelo mesmo motor. A estrutura atende a estes requisitos:

Motor único

O mesmo fluxo de criação e a mesma máquina de estados servem todos os tipos. O veicular entrou sem mudar o motor.

Processo pai, segmento filho

Os dados comuns ficam na tabela PROCESSO e os do imóvel em PROCESSO_IMOBILIARIO (herança JPA JOINED).

Negócio sem HTTP

Toda a regra fica no processo-core. O REST fica no processo-app.

CQRS

A escrita (processo-core) e a leitura (processo-query) não se enxergam.

Integrações isoladas

Sistemas externos ficam atrás de ports. A impressão é descartável: apagar o módulo a remove.

Estados com o padrão State

Cada situação é um objeto que sabe quais eventos aceita. Não há if sobre a situação no motor.

Fluxos de escrita

Criar

POST /processos/imobiliarios com o corpo abaixo responde 201 {"id", "numero"} e um Location para o detalhe.

{
  "proponente": {"nome": "Ana Souza", "cpf": "52998224725"},
  "valor": 400000.00,
  "imovel": {"matricula": "12345", "tipo": "RESIDENCIAL", "valorAvaliacao": 500000.00, "uf": "SP"}
}
  1. App. O ProcessoImobiliarioResource converte o JSON numa Solicitacao<DadosImobiliarios> e chama MotorDeProcessamento.criar.
  2. Motor escolhe o segmento pela classe dos dados (DadosImobiliarios → SegmentoImobiliario).
  3. Regras comuns: nome obrigatório, CPF com dígitos verificadores corretos, valor maior que zero.
  4. Regras do segmento: matrícula, UF, tipo, avaliação, limite de 80% (residencial) ou 60% (comercial) da avaliação e, por último, a consulta ao banco: não pode haver processo aberto para a mesma matrícula na mesma UF.
  5. Sistema externo: o port SituacaoCadastral consulta o cadastro do CPF. É a última regra, para não chamar o sistema externo à toa. Até aqui nada roda em transação.
  6. Transação curta: a partir daqui, dentro de Transacoes.executar. O número é IMO-2026-000042, com o prefixo do segmento, o ano e a sequence SEQ_NUMERO_PROCESSO, que é única para todos os segmentos.
  7. Gravação: o segmento grava PROCESSO e PROCESSO_IMOBILIARIO com um @Insert da entidade filha.
  8. Evento: o motor publica ProcessoCriado. Depois do commit, a impressao pede o PDF de abertura. Se o sistema de PDF falhar, o erro fica no log e o processo continua gravado.

Qualquer regra violada responde 422 {"motivo": "..."}, sem gerar número, gravar ou publicar. Se o sistema de cadastro estiver fora do ar ou estourar o timeout (2 s), a resposta é 503. O POST /processos/veiculares segue o mesmo fluxo, com outro corpo (veiculo: placa, ano, FIPE).

Processar e cancelar (iguais para todos os tipos)

Os endpoints são POST /processos/{id}/processamento, que responde 200 {"situacao", "motivo"}, e POST /processos/{id}/cancelamento, que responde 204.

  1. Qual tipo: o motor lê a coluna SEGMENTO (port Processos) e escolhe o segmento pelo código. O segmento carrega o processo inteiro.
  2. ABERTO → EM_PROCESSAMENTO: o State valida e a troca é gravada numa transação curta por compare-and-set: update PROCESSO ... where ID = ? and SITUACAO = 'ABERTO'. Se nenhuma linha mudou, outra requisição chegou antes, e a resposta é 409. Não há lock pessimista: ele prenderia a conexão durante a avaliação, que pode chamar sistemas externos.
  3. Avaliação do tipo, fora de transação: segmento.avaliar(processo) devolve aprovado ou recusado com motivo. O imobiliário recusa acima de R$ 1.000.000; o veicular recusa veículo com mais de 10 anos.
  4. EM_PROCESSAMENTO → CONCLUIDO ou RECUSADO: pelo State, em outra transação curta, guardando o motivo da recusa.

Cancelar: o processo é carregado e passa de ABERTO para CANCELADO numa transação. Em qualquer outro estado a resposta é 422, por exemplo "Processo CONCLUIDO não pode ser cancelado". Processo inexistente responde 404.

As migrations contam a história: a V1 cria o schema, a V2 acrescenta as situações do processamento e o motivo da recusa, e a V3 cria a tabela do tipo veicular. Tipo novo é sempre uma migration nova com a tabela filha.

Herança no banco, genéricos no domínio

No banco, o processo imobiliário é uma subclasse JPA: a entidade filha estende ProcessoEntity. No domínio, ele é um Processo<DadosImobiliarios>, ou seja, os dados do processo carregam os do segmento.

  • Os records do domínio não podem estender classes.
  • Um sealed não funcionaria entre módulos Maven.
  • Para o motor, todo processo é igual e só D muda.

Cada segmento converte o próprio Processo<D> na própria entidade filha, no mapper de persistência.

Por que o jpa-core fica fora do processo-core

Escrita e leitura precisam das mesmas entidades e não podem se enxergar. Com as entidades num módulo próprio:

  • o query depende só do schema;
  • o mapeamento existe uma vez só;
  • o HQL dos dois lados é validado contra a mesma fonte;
  • as migrations têm uma única sequência de versões.

O jpa-core não tem regra nenhuma, só descreve o schema.

Motor e segmentos

O motor depende só da interface Segmento. Cada segmento é um bean CDI que a implementa:

public interface Segmento<D extends DadosDoSegmento> {
    String codigo();                                // "IMOBILIARIO", gravado como discriminador
    String prefixo();                               // "IMO", compõe o número
    Class<D> tipoDosDados();                        // como o motor escolhe o segmento
    Especificacao<Solicitacao<D>> regras();        // regras próprias, aplicadas depois das comuns
    void salvar(Processo<D> processo);              // grava pai + filha
    Optional<Processo<D>> carregar(UUID id);        // lê pai + filha
    Avaliacao avaliar(Processo<D> processo);       // decisão do processamento (fora de transação)
}
  • Descoberta: o motor recebe @Any Instance<Segmento<?>>. Todo bean que implementa Segmento é encontrado sem registro manual. Dois segmentos com o mesmo código ou o mesmo tipo de dados fazem o motor recusar a inicialização.
  • Regras: Especificacao<T> devolve o motivo da violação. Regras se compõem com e(...), e a primeira que falha define a mensagem do 422.
  • Mesmo módulo, fronteira por ArchUnit: motor e segmentos ficam no processo-core, em pacotes diferentes. Uma regra impede o motor de importar qualquer coisa de segmento.. e outra impede um segmento de ver outro.
  • Endpoint por segmento: o corpo da requisição pertence ao segmento, e todos entregam ao mesmo MotorDeProcessamento.criar. A listagem é uma só, porque mostra apenas os campos comuns.

Máquina de estados (padrão State)

ABERTO ──iniciarProcessamento──► EM_PROCESSAMENTO ──concluir──► CONCLUIDO
   │                                    └───recusar───► RECUSADO
   └──cancelar──► CANCELADO

A máquina é a mesma para todos os tipos e mora em core.motor.domain.state. Os papéis do GoF:

PapelClasseO que faz
ContextProcesso<D>Guarda a Situacao (o valor persistido) e delega cada evento ao estado correspondente. Imutável: cada evento devolve uma cópia na nova situação.
Stateenum SituacaoUm método por evento. Por padrão todo evento lança TransicaoInvalidaException.
ConcreteStatesas constantes ABERTO, EM_PROCESSAMENTO, CONCLUIDO, RECUSADO, CANCELADOCada uma sobrescreve só as transições que permite. As finais não sobrescrevem nada.
 
public enum Situacao {
    ABERTO {
        public Situacao iniciarProcessamento() { return EM_PROCESSAMENTO; }
        public Situacao cancelar() { return CANCELADO; }
    },
    EM_PROCESSAMENTO {
        public Situacao concluir() { return CONCLUIDO; }
        public Situacao recusar() { return RECUSADO; }
    },
    CONCLUIDO, RECUSADO, CANCELADO;

    public Situacao concluir() { throw new TransicaoInvalidaException(this, "concluído"); }
    // iniciarProcessamento(), recusar() e cancelar(): o mesmo
}

// No Context:
public Processo<D> cancelar() { return em(situacao.cancelar(), null); }
  • Pacote autocontido: o estado não depende de nada do resto do domínio (tem a própria exceção), então não forma ciclo com o Processo, que o usa.
  • Um enum, não uma classe por estado: é o mesmo padrão, com a máquina inteira num arquivo. O valor persistido e o comportamento são o mesmo objeto, então não há tradução entre os dois.
  • Teste: o SituacaoTest é uma tabela com todos os estados × todos os eventos. Uma transição nova é uma linha na tabela e um método numa constante.
  • Erros: transição inválida responde 422, e conflito de concorrência (compare-and-set) responde 409.

O cliente de cadastro

  • CadastroClient é o REST Client real (GET /situacoes/{documento}), com endereço em quarkus.rest-client.cadastro.url (variável CADASTRO_URL).
  • RespostaCadastro (dto/) é o modelo do sistema externo e não sai do pacote cadastro.
  • SituacaoCadastralAdapter (adapter/) implementa o port, e RespostaCadastro.regular() converte a resposta em true ou false. Erro HTTP, de rede ou timeout vira SistemaExternoIndisponivelException (do domínio), e a resposta é 503.

A impressão (descartável)

ImpressaoDeProcessos observa ProcessoCriado com TransactionPhase.AFTER_SUCCESS e envia um Documento ao SistemaDePdf (REST Client). O documento é montado assim:

  • modelo: abertura-processo-<segmento>;
  • referência: o número do processo;
  • dados do segmento: seguem em processo.dados.

Para remover a impressão, apague o módulo, a entrada no POM pai, a dependência no app e a propriedade quarkus.rest-client.sistema-pdf.url.

Integração no app, no core ou à parte?

  • No core: traria HTTP e os modelos dos sistemas externos para dentro da regra de negócio.
  • No app: ele viraria um depósito de entrada e saída, com as dependências de todos os sistemas.
  • Em integracoes: um pacote por sistema atende enquanto os sistemas forem pequenos e estáveis.
  • Módulo próprio: para sistema com ciclo de vida próprio, dependências pesadas (SOAP, MQ, código gerado) ou descartável.

Repositórios Jakarta Data

As interfaces @Repository, como ProcessoQueries, NumeracaoRepository e ProcessoImobiliarioRepository, não têm implementação escrita à mão. O caminho até virarem beans:

  1. Compilação: o hibernate-processor (annotation processor no POM pai) gera ProcessoQueries_ em target/generated-sources/annotations. É Java comum e legível: um bean @Dependent que recebe uma StatelessSession e executa cada @Query.
  2. Validação: o processor confere o HQL contra as entidades do jpa-core. Campo ou entidade inexistente é erro de compilação.
  3. Empacotamento: o jandex-maven-plugin indexa o jar, e o Quarkus descobre o bean gerado.
  4. Build do Quarkus: o CDI liga ProcessoQueries → ProcessoQueries_. No core, o repository estende o port de persistência: o bean gerado implementa o port, e os métodos default convertem com o mapper. O motor nem sabe que é Jakarta Data.

Em relação ao Panache, a parte implícita fica no build (código gerado e validado), e não em tempo de execução (strings de consulta e projeção por reflexão). O query também não herda persist nem delete.

Regras de arquitetura

O Maven só impede o que não está no classpath. O resto é garantido pelo ArchUnit (API core dentro de @Test comum, porque o engine JUnit 5 do ArchUnit não roda sob o JUnit 6 do BOM).

processo-core · ArquiteturaTest

O motor não conhece segmentos. Segmentos não se enxergam. Camadas: domain só usa Java puro (e o domínio do motor); application só conhece ports, nunca adapters.

processo-app · ArquiteturaModulosTest

Core e query não se enxergam. Ninguém depende da impressão, das integrações nem do app. As integrações só usam o domínio e os port/out do core e não se enxergam entre si. O jpa-core não conhece o resto. HTTP só no app, na impressão e nas integrações. O app entra no core pelo motor, nunca pelos ports de saída, SPI ou adapters, e não usa entidades JPA. No REST, dto não conhece resource. Não há ciclos entre pacotes, e toda classe pertence a um módulo registrado.

Build, Sonar e cobertura

Cada módulo usa o target/ padrão. O CI roda dois passos:

mvn clean verify                                     # testes + relatórios (report-aggregate no app)
mvn org.sonarsource.scanner.maven:sonar-maven-plugin:3.6.0.1398:sonar \
    -Dsonar.sources=pom.xml,src/main -DskipTests ...  # análise, sem clean

Receitas

Adicionar um tipo (segmento)

  1. jpa-core: entidade filha de ProcessoEntity com @DiscriminatorValue e @PrimaryKeyJoinColumn, mais a migration da tabela filha.
  2. processo-core, pacote segmento.<nome>:
    • domain/model: record que implementa DadosDoSegmento;
    • domain/rule: regras em Especificacao;
    • application/port/out: port de persistência (gravar e carregar);
    • application/service: bean que implementa Segmento<D>, incluindo carregar e avaliar;
    • adapter/outbound/persistence: repository/ (implementa o port) e mapper/.
  3. processo-query: projeção e consulta de detalhe na filha. A listagem já inclui o segmento novo.
  4. processo-app, em adapter/inbound/rest: resource/ com POST /processos/<segmento> e GET .../{id}, o request em dto/ e o paraSolicitacao() no próprio request.
  5. Testes unitários do segmento no motor real e um Tipo novo em CicloDeVidaPorTipoIT.tipos(). O motor, a máquina de estados, a impressão e os endpoints de ciclo de vida não mudam. O commit do veicular é o exemplo.

Adicionar uma integração síncrona

  1. Port em application/port/out do core: no motor se vale para todos os segmentos, no segmento se é só dele. Use-o numa regra.
  2. Pacote integracoes.<sistema>:
    • client/: o REST Client;
    • dto/: o modelo do sistema externo, com a conversão para o domínio (ou um mapper/, se ela tiver lógica);
    • adapter/: implementa o port;
    • simulação @IfBuildProfile("dev"), se quiser rodar o dev sem o sistema.
  3. application.properties: quarkus.rest-client.<chave>.url.
  4. IT: um servidor falso como o CadastroFalso, ligado com @WithTestResource.

Adicionar uma consulta

Declare o método em repository/ProcessoQueries com @Query e select new para um record top-level e plano em dto/, e exponha num resource do app. O HQL é validado na compilação do processo-query.

Adicionar um novo módulo Maven

Faça quatro registros:

  • <module> e dependencyManagement no POM pai;
  • dependência direta no processo-app;
  • jandex-maven-plugin no POM do módulo, se ele tiver beans;
  • pacote raiz em MODULOS no ArquiteturaModulosTest.

Armadilhas

  • Índice de entidades no jar. Sem o copy-resources do entity/index no jpa-core, o HQL dos outros módulos deixa de ser validado, sem aviso.
  • select new não instancia records aninhados. Use projeções top-level e planas.
  • NUMBER do Oracle não guarda zeros à direita: 400000.00 volta como 400000 e sai assim no JSON. Compare valores numericamente nos testes.
  • @QueryParam com enum inválido responde 404, não 400, como o JAX-RS define.
  • %prod e ITs. Configurar a URL do banco em %prod desliga o Dev Services nos ITs. O jar recebe a conexão por variáveis de ambiente.
  • Nomes de coluna explícitos. O Quarkus não converte dataAbertura em DATA_ABERTURA por padrão.
  • Sistema externo nos ITs. O test resource roda na JVM do teste, e o mapa devolvido por start() vira configuração do jar, que roda em outro processo.
  • POM pai desatualizado no ~/.m2. Um install parcial sem o POM pai deixa dependências transitivas invisíveis para quem constrói só o app. Sintoma: Unsatisfied dependency de beans que existem. Rode mvn install -N na raiz.

Pontos em aberto

O exemplo cumpre os requisitos, e os testes de unidade, integração e arquitetura passam. Antes de levar o padrão para produção, estes pontos merecem decisão:

Processo preso em EM_PROCESSAMENTOO processar grava EM_PROCESSAMENTO, avalia fora de transação e grava o estado final noutra transação. Se a aplicação cair, ou a avaliação lançar exceção, entre as duas, o processo fica em EM_PROCESSAMENTO. Isso exige uma rotina de recuperação, que reprocesse ou devolva para ABERTO os processos parados há mais de N minutos.
Corrida na regra da matrícula"Não pode haver processo em andamento para a mesma matrícula" é verificado e depois gravado. Duas requisições simultâneas podem passar juntas. A situação está no pai e a matrícula na filha, então um índice único condicional não resolve sozinho. As saídas são:
  • trava pessimista;
  • tabela de controle com chave única;
  • copiar a situação para a filha.
Sem histórico de transiçõesSó a situação atual e o motivo da última recusa ficam gravados. Em pagamentos, costuma ser necessário saber quem mudou o quê e quando. Uma tabela de transições, gravada pelo motor na mesma transação do compare-and-set, resolve.
Impressão síncrona e sem retentativaO PDF é pedido depois do commit, na mesma thread da requisição, e uma falha só vai para o log. Se o PDF não puder se perder, o próximo passo é uma outbox (tabela de pendências com reenvio) dentro do módulo impressao.
Listagem sem paginaçãoGET /processos devolve tudo. Use PageRequest do Jakarta Data ou limit/offset antes de ter volume.
REST e consultas com 0% no SonarSó os ITs exercitam o app e o query, e eles ficam fora da cobertura. Se o quality gate cobrar cobertura de código novo, considere @QuarkusTest para essas camadas.
Lacunas de numeraçãoA sequence é consumida antes da gravação. Uma falha na gravação deixa um número sem uso. Isso costuma ser aceitável, mas precisa ser decidido se a numeração tiver de ser contínua.
