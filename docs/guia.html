Guia do projeto Processo

Processos de vários tipos com um motor único, em Maven multi-module: onde fica cada coisa, por quê, e como estender.

Java 25 Quarkus 3.33 Oracle + Flyway Jakarta Data Padrão State ArchUnit JaCoCo + Sonar

Em um minuto

Há dois tipos de processo, imobiliário e veicular. Os dois são criados, processados e cancelados pelo mesmo motor; o que muda de um tipo para outro fica num segmento.

Motor único

Mesmo fluxo e mesma máquina de estados para todos os tipos. O veicular entrou sem mudar o motor.

Pai e filho

Dados comuns em PROCESSO, dados do tipo na tabela filha (herança JPA JOINED).

Escrita e leitura separadas

processo-core escreve, processo-query lê. Um não enxerga o outro.

Bordas trocáveis

REST no app; cadastro e PDF atrás de interfaces, em integracoes.

Pastas e pacotes

O motor e cada segmento seguem as mesmas pastas. A dependência só vai para dentro: adapter → application → domain.

PastaO que vai lá
domain/Java puro: model (records), state (máquina de estados), rule (regras), exception.
application/port/outInterfaces do que o core precisa de fora: banco, sistemas externos, transação.
application/port/spiO contrato que cada segmento implementa (Segmento).
application/serviceO motor e os segmentos.
adapter/outbound/persistencerepository/ (Jakarta Data) e mapper/ (domínio ↔ entidade).
adapter/inbound/restNo app: resource/, dto/ e exception/ (exceção → HTTP).
configProducers CDI, como o Clock.
Duas regras para não criar código à toa
  • Interface só onde há costura real: entre módulos (Segmento, SituacaoCadastral, GeradorDeDocumentos). Dentro do módulo, injete a classe: o REST injeta o MotorDeProcessamento direto.
  • Mapper só quando a conversão tem lógica: conversão de uma linha é método do DTO (request.paraSolicitacao(), ProcessoCriadoResponse.de(p)). Classe em mapper/ só para domínio ↔ entidade.

Fluxos

Criar: POST /processos/imobiliarios

{
  "proponente": {"nome": "Ana Souza", "cpf": "52998224725"},
  "valor": 400000.00,
  "imovel": {"matricula": "12345", "tipo": "RESIDENCIAL", "valorAvaliacao": 500000.00, "uf": "SP"}
}
  1. REST: o resource converte o JSON (request.paraSolicitacao()) e chama motor.criar.
  2. Segmento: o motor escolhe pelo tipo dos dados (DadosImobiliarios → SegmentoImobiliario).
  3. Regras, fora de transação: primeiro as comuns (nome, CPF, valor), depois as do segmento (limite da avaliação, matrícula sem processo em andamento) e por último o sistema de cadastro, para não chamá-lo à toa.
  4. Transação curta: gera o número (IMO-2026-000042) e grava pai e filha.
  5. Depois do commit: o motor pede o PDF de abertura (GeradorDeDocumentos). Se o sistema falhar, só loga: o processo já está gravado.

Respostas: 201 {"id", "numero"}; regra violada 422 {"motivo"}; cadastro fora do ar 503. O veicular é igual, com veiculo (placa, ano, FIPE) no corpo.

Processar e cancelar (iguais para todos os tipos)

  1. POST /processos/{id}/processamento: o motor lê o tipo na coluna SEGMENTO e o segmento carrega o processo.
  2. ABERTO → EM_PROCESSAMENTO numa transação curta, com compare-and-set: update ... where ID = ? and SITUACAO = 'ABERTO'. Se nenhuma linha mudou, outra requisição chegou antes: 409.
  3. segmento.avaliar, fora de transação: o imobiliário recusa acima de R$ 1.000.000, o veicular recusa veículo com mais de 10 anos.
  4. EM_PROCESSAMENTO → CONCLUIDO ou RECUSADO noutra transação curta. Responde 200 {"situacao", "motivo"}.

POST /processos/{id}/cancelamento só vale para ABERTO (204). Transição inválida dá 422 e processo inexistente 404.

Por que não lock pessimista?Ele prenderia a conexão durante a avaliação, que pode chamar sistemas externos. O compare-and-set garante o mesmo sem travar.

Consultar

GET /processos?situacao=ABERTO&pagina=1&tamanho=20 lista todos os tipos a partir da tabela pai, paginado ({"itens", "pagina", "tamanho", "total"}; tamanho até 100, fora disso 400). GET /processos/imobiliarios/{id} (ou /veiculares/{id}) consulta a filha. As duas vão direto ao processo-query, sem passar pelo domínio, e as projeções dele já são a resposta.

Modelo de dados

PROCESSO                                   PROCESSO_IMOBILIARIO
  ID              RAW(16)  PK   ◄─────────   PROCESSO_ID     RAW(16)  PK, FK
  NUMERO          VARCHAR2 único             MATRICULA, TIPO_IMOVEL, VALOR_AVALIACAO, UF
  SEGMENTO        VARCHAR2 (discriminador)
  PROPONENTE_NOME, PROPONENTE_CPF            PROCESSO_VEICULAR
  VALOR           NUMBER(15,2)  ◄─────────   PROCESSO_ID     RAW(16)  PK, FK
  SITUACAO        VARCHAR2                   PLACA, ANO_FABRICACAO, VALOR_FIPE
  MOTIVO_RECUSA, DATA_ABERTURA

SEQ_NUMERO_PROCESSO   numeração única para todos os tipos
  • No banco, o tipo é uma subclasse JPA da entidade pai. No domínio, é um Processo<DadosImobiliarios>: records não herdam, e para o motor só o D muda.
  • Por que o jpa-core é separado: escrita e leitura usam as mesmas entidades sem se enxergar. O mapeamento e as migrations existem uma vez só.
  • Tipo novo é sempre uma migration nova com a tabela filha.

Motor e segmentos

O motor só conhece a interface Segmento. Cada tipo é um bean que a implementa:

public interface Segmento<D extends DadosDoSegmento> {
    String codigo();                                // "IMOBILIARIO", gravado como discriminador
    String prefixo();                               // "IMO", compõe o número
    Class<D> tipoDosDados();                        // como o motor escolhe o segmento
    Especificacao<Solicitacao<D>> regras();        // aplicadas depois das comuns
    void salvar(Processo<D> processo);              // grava pai + filha
    Optional<Processo<D>> carregar(UUID id);        // lê pai + filha
    Avaliacao avaliar(Processo<D> processo);       // decisão do processamento
}

O motor recebe todos os beans Segmento pelo CDI, sem registro manual. Cada regra (Especificacao) devolve o motivo da violação; regras se compõem com e(...), e a primeira que falha vira a mensagem do 422.

Do motor (igual para todos)Do segmento (cada um o seu)
Fluxo de criação, regras comuns, cadastroDados, regras próprias, endpoint de criação
Numeração, transações, eventosPrefixo, tabela filha, consulta de detalhe
Máquina de estados, processar e cancelarA decisão do processamento (avaliar)
Quando um tipo deve sair do motorSe um tipo precisar de estados ou etapas que os outros não têm, dê a ele um fluxo próprio. Encher o Segmento de flags e casos especiais é o sinal.

Máquina de estados

ABERTO ──iniciarProcessamento──► EM_PROCESSAMENTO ──concluir──► CONCLUIDO
   │                                    └───recusar───► RECUSADO
   └──cancelar──► CANCELADO

É o padrão State num enum: cada constante de Situacao sobrescreve só as transições que aceita, e o resto lança TransicaoInvalidaException (422). O Processo só delega; não há if sobre a situação.

public enum Situacao {
    ABERTO {
        public Situacao iniciarProcessamento() { return EM_PROCESSAMENTO; }
        public Situacao cancelar() { return CANCELADO; }
    },
    EM_PROCESSAMENTO {
        public Situacao concluir() { return CONCLUIDO; }
        public Situacao recusar() { return RECUSADO; }
    },
    CONCLUIDO, RECUSADO, CANCELADO;

    public Situacao concluir() { throw new TransicaoInvalidaException(this, "concluído"); }
    // iniciarProcessamento(), recusar() e cancelar(): o mesmo
}

// No Processo:
public Processo<D> cancelar() { return em(situacao.cancelar(), null); }

Transição nova: um método numa constante e uma linha na tabela do SituacaoTest.

Integrações

Cadastro

  • CadastroClient: o REST Client, com a URL em CADASTRO_URL.
  • SituacaoCadastralAdapter: implementa a interface do core. Erro HTTP, de rede ou timeout (2 s) vira 503.
  • CadastroClientSimulado: responde sempre REGULAR, só no quarkus:dev.
@IfBuildProfile("dev")             // só existe no build de dev
@Alternative @Priority(1)          // ganha do REST Client gerado
@RestClient @ApplicationScoped
public class CadastroClientSimulado implements CadastroClient { ... }

No dev responde a simulação; no jar, o REST Client real; nos ITs, o REST Client contra o servidor falso CadastroFalso. Se o módulo integracoes sair do app, o build falha, não a produção.

PDF

Mesmo molde do cadastro, no pacote integracoes.pdf. O motor chama o port GeradorDeDocumentos depois do commit; o GeradorDeDocumentosAdapter envia Documento.deAbertura(processo) ao sistema de PDF (SISTEMA_PDF_URL, timeout de 2 s) e traduz falhas para SistemaExternoIndisponivelException, que o motor só loga. No dev, o SistemaDePdfSimulado só registra o pedido no log.

Repositórios Jakarta Data

As interfaces @Repository não têm implementação escrita à mão:

  1. Compilação: o hibernate-processor gera ProcessoQueries_ em target/generated-sources (Java comum, dá para ler) e valida o HQL contra as entidades. Erro de campo é erro de compilação.
  2. Empacotamento: o jandex-maven-plugin indexa o jar para o Quarkus achar o bean.
  3. No core: o repository estende a interface de port/out, e os métodos default convertem pelo mapper. O motor não sabe que é Jakarta Data.

Arquitetura e testes

O Maven só impede o que não está no classpath; o resto o ArchUnit garante:

  • ArquiteturaTest (core): o motor não conhece segmentos, segmentos não se enxergam, domain é Java puro, application não conhece adapters.
  • ArquiteturaModulosTest (app): core e query não se enxergam; ninguém depende de integrações nem do app; HTTP só nas bordas; o app entra no core pelo motor; sem ciclos.
MóduloTestesDocker
processo-coreTabela de estados × eventos, regras, motor com segmentos falsos, cada segmento no motor real.não
integracoesConversão da resposta do cadastro, documento enviado ao PDF, falha do cliente vira indisponibilidade.não
processo-appITs contra o jar com Oracle: o mesmo ciclo de vida para cada tipo (inclusive 8 processamentos simultâneos, só um vence), os casos da criação, a paginação e health/OpenAPI.sim
 
mvn -pl processo-core,integracoes -am test   # unitários, sem Docker
mvn verify                                    # tudo, com os ITs
mvn install -DskipTests && mvn -pl processo-app quarkus:dev   # dev: Oracle via Dev Services

No dev: Swagger UI em /q/swagger-ui. Em qualquer ambiente: contrato em /q/openapi e health em /q/health (o readiness confere o banco).

Build e Sonar

mvn clean verify                                     # testes + JaCoCo agregado no app
mvn org.sonarsource.scanner.maven:sonar-maven-plugin:3.6.0.1398:sonar \
    -Dsonar.sources=pom.xml,src/main -DskipTests ...  # análise, sem clean
  • Todos os módulos leem o relatório agregado do app (sonar.coverage.jacoco.xmlReportPaths no POM pai).
  • O report-aggregate só enxerga dependências diretas: por isso o app declara todos os módulos.

  • Os ITs contam como testes, mas não como cobertura (rodam o jar em outro processo).

Receitas

Novo tipo de processo

  1. jpa-core: entidade filha (@DiscriminatorValue) e a migration.
  2. processo-core/segmento/<tipo>: o record de dados, as regras, a interface de persistência, o bean Segmento (com avaliar), o repository e o mapper.
  3. processo-query: a consulta de detalhe. A listagem já inclui o tipo novo.
  4. processo-app: resource com POST e GET {id}, e o request com paraSolicitacao().
  5. Testes: os do segmento e um Tipo novo em CicloDeVidaPorTipoIT.tipos().

O motor, os estados e as integrações não mudam. O commit do veicular é o exemplo.

Nova integração

  1. Interface em port/out do core (do motor ou do segmento que a usa), chamada numa regra ou num passo do fluxo.
  2. Pacote integracoes.<sistema> com client/, dto/, adapter/ e, se quiser, a simulação de dev.
  3. URL em application.properties e um servidor falso no IT (@WithTestResource).

Nova consulta

Método com @Query e select new em ProcessoQueries, record em dto/ e endpoint no app.

Novo módulo Maven

Registre em quatro lugares: <module> e dependencyManagement no POM pai, dependência no app, jandex-maven-plugin (se tiver beans) e MODULOS no ArquiteturaModulosTest.

Armadilhas

  • Índice de entidades: sem o copy-resources do entity/index no jpa-core, o HQL dos outros módulos para de ser validado, sem aviso.
  • select new não instancia records aninhados: use projeções planas.
  • NUMBER do Oracle perde zeros à direita (400000.00 volta 400000). Compare números, não texto.
  • Enum inválido em @QueryParam responde 404, não 400.
  • URL do banco em %prod desliga o Dev Services nos ITs.
  • Servidor falso nos ITs roda na JVM do teste; o mapa de start() vira configuração do jar, que roda em outro processo.
  • Colunas precisam de nome explícito: o Quarkus não converte dataAbertura em DATA_ABERTURA.
  • Unsatisfied dependency de bean que existe: POM pai velho no ~/.m2. Rode mvn install -N na raiz.
