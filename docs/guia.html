Guia do projeto Processo

O que o sistema faz, como as peças se encaixam e por onde começar. Leitura de uns 10 minutos.

Java 25 Quarkus 3.33 Oracle Camadas num módulo só

Em um minuto

O sistema cuida de processos de crédito de consórcio: pedidos que nascem abertos e terminam concluídos, recusados ou cancelados. Há duas modalidades, imobiliária e veicular, e as duas andam pelo mesmo motor. O que muda de uma modalidade para outra fica num pedaço separado.

Quatro camadas

Apresentação, negócio, integração e persistência, cada uma numa pasta. Todas usam o mesmo modelo.

Um motor para todos

Criar, processar e cancelar funcionam igual para qualquer modalidade. A veicular entrou sem mudar o motor.

Modalidades como peças

Cada modalidade traz só o que é dela: a tabela, as regras e a decisão de aprovar ou recusar.

Gravar e ler por caminhos diferentes

Gravar passa pelo negócio e pelas regras; as telas leem direto do banco, no formato delas.

CRUD sem cerimônia

O que é só cadastro (agências) segue um caminho bem mais curto, sem motor.

Regras viram teste

Quem pode usar quem está escrito em testes: quebrou a regra, quebrou o build.

As camadas

O projeto é um módulo só, dividido em pastas por responsabilidade. Cada camada só pode usar as que estão abaixo dela. A seta mostra quem usa quem.

CamadaO que temO que não pode
apresentacaoPor onde os pedidos chegam: a API e a fila. Traduz o pedido e a resposta.Ter regra de negócio ou gravar direto no banco.
negocioA lógica do sistema: o motor, uma pasta por modalidade e o cadastro de agências.Saber que existe HTTP ou fila.
integracaoA conversa com sistemas de fora: cadastro e PDF.Deixar o formato do sistema de fora vazar.
persistenciaA conversa com o banco: gravar e ler entidades, e as consultas das telas.Ter regra de negócio.
modeloO vocabulário comum: as entidades (tabelas), os estados e os dados validados.Usar qualquer camada.

Por que um programa só, e não vários serviços? Com até 1.000 usuários por dia em horário comercial, um programa dá conta com folga, e o pagamento e a situação do processo mudam juntos numa única transação. E o modelo ainda muda a cada modalidade nova: dentro de um programa só, mudar uma fronteira é refatorar. Os prós e contras estão na ADR 0013; o porquê das camadas, na ADR 0014.

A vida de um processo

            processar                     aprovado
ABERTO ──────────────────► EM_PROCESSAMENTO ─────────► CONCLUIDO
   │                                │
   │ cancelar                       │ recusado
   ▼                                ▼
CANCELADO                       RECUSADO (com o motivo)

Criar

  1. O pedido chega pela API (POST /processos/imobiliarios) ou pela fila e vira um processo ainda sem número.
  2. As regras conferem: primeiro as que valem para todos (nome, CPF, valor), depois as da modalidade (ex.: a avaliação do imóvel) e, por último, o sistema de cadastro, para não chamá-lo à toa.
  3. O processo é gravado com um número (IMO-2026-000042) e fica ABERTO.
  4. O PDF de abertura é pedido. Se o sistema de PDF falhar, o processo continua criado.

Processar e cancelar

  1. O processo vai para EM_PROCESSAMENTO. Se duas pessoas pedirem ao mesmo tempo, só uma consegue; a outra recebe um aviso de conflito.
  2. A modalidade decide: a imobiliária recusa acima de R$ 1.000.000; a veicular recusa veículo com mais de 10 anos.
  3. O processo termina CONCLUIDO ou RECUSADO, com o motivo.

Cancelar só vale enquanto o processo está ABERTO.

As respostas da API

CódigoQuando
201 / 200 / 204Deu certo (criado / processado / cancelado).
422Uma regra recusou o pedido. O motivo vem no campo detail.
404O processo não existe.
409Outra pessoa mudou o processo ao mesmo tempo. Tente de novo.
503O sistema de cadastro está fora do ar.

Todo erro vem no mesmo formato (Problem Details):

{"type": "/problemas/regra-violada", "title": "Regra de negócio violada", "status": 422,
 "detail": "CPF inválido: 12345678900"}
Pela fila, a mesma criaçãoUma mensagem na fila processos.imobiliarios.novos cria o processo como a API. Se a mesma mensagem chegar duas vezes (o que é normal em fila), o processo não é criado de novo: o id da mensagem serve de chave. A resposta, criado ou recusado, volta em outra fila.

Motor, modalidades e estados

O motor (ProcessoService) faz tudo o que é igual para todas as modalidades. A modalidade só preenche o que é dela:

O motor faz (igual para todas)A modalidade faz (cada uma a sua)
A ordem dos passos de criar, processar e cancelarOs dados próprios (imóvel, veículo), na entidade dela
As regras comuns e a consulta ao cadastroAs regras próprias
O número do processo e a gravaçãoO prefixo do número e a decisão de aprovar ou recusar
Os estados e as mudanças permitidasA tabela própria no banco

Uma modalidade nova é uma entidade filha de Processo e uma classe que implementa Modalidade, com as regras e a decisão:

// resumido
@ApplicationScoped
public class ModalidadeVeicular implements Modalidade<ProcessoVeicular> {
    public Class<ProcessoVeicular> tipo() { return ProcessoVeicular.class; }
    public String prefixo() { return "VEI"; }
    public Especificacao<ProcessoVeicular> regras() { return RegrasVeiculares.TODAS; }
    public Avaliacao avaliar(ProcessoVeicular processo) { /* aprova ou recusa */ }
}

Os estados ficam num enum. Cada estado diz para onde pode ir; qualquer outra mudança é recusada com 422:

// resumido: no código, cada transição é um método que devolve o próximo estado
public enum Situacao {
    ABERTO           { iniciarProcessamento() → EM_PROCESSAMENTO; cancelar() → CANCELADO },
    EM_PROCESSAMENTO { concluir() → CONCLUIDO; recusar() → RECUSADO },
    CONCLUIDO, RECUSADO, CANCELADO;   // finais: não vão para lugar nenhum
}
Quando uma modalidade não cabe no motorSe uma modalidade precisar de estados ou passos que as outras não têm, ela ganha um fluxo próprio. Encher o motor de exceções para uma modalidade só é o sinal de alerta.

Sistemas externos

Toda conversa com um sistema de fora fica na camada integracao, numa pasta por sistema. O negócio chama uma classe (CadastroIntegracao, PdfIntegracao) que esconde o HTTP, o formato do sistema de fora e os erros dele.

SistemaPara quêSe cair
CadastroConfere a situação do CPF antes de criar.A criação para e responde 503.
PDFGera o documento de abertura depois de criar.O processo continua criado; a falha vai para o log.

No modo de desenvolvimento (quarkus:dev) os dois são simulados: dá para rodar tudo sem os sistemas de verdade. Nos testes, servidores falsos fazem o papel deles.

Quando é só cadastro

Nem tudo precisa de motor. Um cadastro de agências só inclui, altera, exclui e consulta: não tem estados, nem modalidades, nem fluxo. Por isso segue o caminho curto, com as mesmas camadas:

  • a entidade, que já nasce validada (Agencia);
  • um serviço que grava e lê (AgenciaService);
  • a API em /agencias (AgenciasResource).

A regra prática: é só CRUD, caminho curto. Se aparecer fluxo, estados ou variação por tipo, aí sim vale o modelo do processo.

Como sabemos que está certo

  • As regras de arquitetura são testes. "A apresentação não grava direto no banco" e "uma modalidade não usa a outra" estão escritos no ArquiteturaTest. Quem quebrar uma regra quebra o build.
  • As regras de negócio são testadas sem banco. Estados, CPF, valor e as regras de cada modalidade rodam em Java puro, em segundos.
  • O motor e o banco são testados juntos. Com um Oracle de verdade, que o Quarkus sobe sozinho no Docker.
  • O sistema é testado de ponta a ponta. Os testes de integração sobem o programa pronto e repetem o mesmo cenário para cada modalidade, inclusive 8 pedidos simultâneos.
mvn test -DexcludedGroups=banco   # rápidos, sem Docker
mvn verify                        # tudo (precisa de Docker)

Glossário

TermoO que é
ProcessoUm pedido que nasce ABERTO e termina concluído, recusado ou cancelado.
ModalidadeUm tipo de processo de consórcio (imobiliária, veicular), com seus dados, regras e decisão. No banco e na API aparece como segmento.
MotorA parte que faz o que é igual para todas as modalidades (ProcessoService).
CamadaUma pasta com uma responsabilidade (apresentação, negócio, integração, persistência) e regras de quem pode usar quem.
EntidadeUma classe ligada a uma tabela do banco. Aqui, as entidades são o próprio modelo do sistema.
ProjeçãoUm formato de leitura montado direto da consulta ao banco, para uma tela.
AvaliaçãoA decisão da modalidade ao processar: aprovado ou recusado com motivo.
Cadastro simplesAlgo que é só CRUD (agências). Vai pelo caminho curto, sem motor.
Value objectUm dado que só existe se for válido, como Cpf e Valor.
EspecificaçãoUma regra que, se não for cumprida, diz o motivo.
Compare-and-setMudar o estado só se ele ainda for o esperado. É o que impede dois processamentos ao mesmo tempo.
Chave de idempotênciaO identificador que impede que o mesmo pedido, repetido, crie dois processos.
Problem DetailsO formato padrão das respostas de erro (type, title, status, detail).
Dev ServicesContainers (Oracle, fila) que o Quarkus sobe sozinho no desenvolvimento e nos testes.

Pontos em aberto

Decidir antes de levar o padrão para produção:

PontoRiscoSaída sugerida
Processo preso em EM_PROCESSAMENTOQueda entre as duas transações do processar.Rotina que reprocessa ou devolve para ABERTO após N minutos.
Corrida na regra da matrículaDuas criações simultâneas passam juntas.Lock, tabela de controle com chave única ou situação copiada para a filha.
Sem histórico de transiçõesNão se sabe quem mudou o quê e quando.Tabela de transições gravada junto do compare-and-set.
PDF sem retentativaChamada síncrona depois do commit (timeout de 2 s); falha só vai para o log.Outbox: tabela de pendências gravada na transação e reenviada por um job.
REST com 0% no SonarSó os ITs exercitam os resources, e eles rodam o jar em outro processo, sem cobertura.@QuarkusTest com RestAssured nos resources, se o gate exigir.
Lacunas de numeraçãoFalha na gravação deixa número sem uso.Aceitar, ou trocar a sequence por um contador travado na transação, se precisar ser contínua.
